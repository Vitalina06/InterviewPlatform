# Платформа для технических собеседований

Веб-система для планирования и проведения технических собеседований: база кандидатов, карточки собеседований, матрица компетенций (оценки 1-5), решение согласующего, генерация PDF-документов, архив.

## Возможности

- Вход по логину и паролю, три роли: **Администратор**, **HR**, **Согласующий**. Каждая роль видит только свои разделы.
- Блокировка входа на 15 минут после 5 неудачных попыток подряд.
- Администратор: создание пользователей и назначение ролей.
- HR: кандидаты (поиск по ФИО), вакансии с компетенциями, собеседования, матрица компетенций, архив и восстановление, PDF-документы (протокол, приглашение, отказ, карточка кандидата).
- Согласующий: просмотр кандидатов и собеседований, решение (Принять / Отклонить / На следующий этап).

## Технологии

| Часть | Технология |
|---|---|
| Backend | C#, .NET 8, ASP.NET Core Web API |
| Реляционная БД | PostgreSQL (Entity Framework Core) |
| NoSQL | MongoDB: журнал аудита и готовые PDF |
| Брокер сообщений | Apache Kafka |
| PDF | QuestPDF, отдельный сервис Worker |
| Логи | Serilog, Logstash, Elasticsearch, Kibana (ELK) |
| Frontend | HTML, CSS, JavaScript |
| Контейнеризация | Docker, docker-compose |
| Тесты | xUnit, Moq |

## Архитектура

    Браузер -> API (ASP.NET Core) -> PostgreSQL    (пользователи, кандидаты, собеседования)
                  |
                  +-> Kafka, топик pdf-requests    -> Worker -> QuestPDF -> MongoDB (PDF)
                  +-> Kafka, топик audit-events    -> Worker -> MongoDB (журнал аудита)

    API и Worker -> JSON-логи в папку logs -> Logstash -> Elasticsearch -> Kibana

PDF генерируются асинхронно: API кладёт задачу в Kafka и сразу отвечает, Worker создаёт файл и сохраняет его в MongoDB, интерфейс опрашивает статус и скачивает готовый документ.

Структура backend: Controllers (HTTP и права доступа), Services (бизнес-логика), Repositories (доступ к данным), Models и DTOs. Сервисы зависят от интерфейсов, зависимости подключаются через внедрение зависимостей (DI).

## Запуск

Нужен Docker Desktop.

1. Скопировать шаблон настроек и заполнить значения:

        cp .env.example .env

   Пример содержимого `.env` (подойдут любые значения):

        POSTGRES_USER=interview
        POSTGRES_PASSWORD=DemoPg2026x
        POSTGRES_DB=interview_db
        MONGO_USER=mongoadmin
        MONGO_PASSWORD=DemoMongo2026x
        JWT_KEY=DemoJwtKeyForLocalRunOnly2026SecretValue
        ADMIN_LOGIN=admin
        ADMIN_PASSWORD=Admin2026x

   Ключ `JWT_KEY` должен быть не короче 32 символов.

2. Запустить все сервисы:

        docker compose up -d --build

3. Открыть приложение: http://localhost:8080

   Swagger: http://localhost:8080/swagger

4. Первый вход: логин и пароль администратора из `.env`. Администратор создаёт пользователей с ролями HR и Согласующий. Затем HR создаёт вакансию, кандидата и собеседование.

Остановка: `docker compose down`, `docker compose down -v`.

## Логи (ELK)

Приложения пишут JSON-логи в папку `logs/`, Logstash отправляет их в Elasticsearch.

1. Открыть Kibana: http://localhost:5601
2. Меню, Stack Management, Data Views, Create data view.
3. Указать `interview-logs-*`, поле времени `@timestamp`.
4. Раздел Discover показывает логи сервисов `api` и `worker`

Журнал аудита (создание собеседований, решения, архивация, запросы документов) хранится в MongoDB, коллекция `audit`.

## Тесты

    dotnet test

Тесты проверяют блокировку входа, хеширование паролей, правила создания собеседований и решение согласующего.

## Безопасность

- Пароли хранятся только в виде хеша BCrypt.
- Аутентификация по JWT, права проверяются на сервере по ролям (атрибут `Authorize`).
- Блокировка входа после 5 неудачных попыток на 15 минут.
- Пароли, ключ JWT и адреса баз вынесены из кода в настройки и переменные окружения. Файл `.env` не попадает в git, в репозитории только шаблон `.env.example`.
- Данные валидируются на сервере (атрибуты в DTO, проверки в сервисах).
- В интерфейсе данные вставляются как текст (`textContent`), а не как HTML, чтобы исключить XSS.
- Запросы к БД идут через Entity Framework (параметризованные запросы), защита от SQL-инъекций.
- Наружу не отдаются хеши паролей: используются отдельные DTO.

## Соответствие ТЗ

Реализованы этапы Must have и Should have: авторизация, пользователи и роли, кандидаты, собеседования, матрица компетенций, решение согласующего, PDF-документы, архивация.

Не реализованы (Could have, опционально): календарь собеседований, рейтинговая таблица кандидатов, фильтрация собеседований по дате.
